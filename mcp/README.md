# Реестр MCP

`registry.yaml` хранит назначение конфигурации, источник, способ установки, условия активации и политику; `locks/mcp.lock.yaml` фиксирует одобренные ревизии. Секреты задаются только ссылкой `env:VARIABLE` или через нативный OAuth.

Нативное состояние остаётся в хранилище самого MCP. В частности, базы codebase-memory, память Serena и сеансы клиентов не переносятся в память проекта. Набор хранит только связь логического проекта с интеграциями в локальном каталоге `projects/<project-id>/integrations/`.

## Учётные данные и OAuth

Для stdio MCP используйте `mcp-creds.example.env` как шаблон: он перечисляет базовые имена переменных пустыми значениями. Скопируйте его в `mcp-creds.env`, заполните нужные поля и импортируйте через `agent-kit mcp creds import --from ./mcp-creds.env`. Значения попадают в machine-local хранилище Kit. Не записывайте literal credentials в registry, нативные конфигурации клиента, Git или аргументы команды. `.env.example` сохранён для совместимости со старыми проверками.

Remote OAuth — отдельный поток: Atlassian, GitLab и Context7 проходят авторизацию в интерфейсе конкретного клиента. OAuth-состояние принадлежит каждому клиенту и профилю отдельно. Если все клиенты намеренно подключены к одному Docker MCP Gateway, авторизацией и OAuth-состоянием владеет Docker Desktop; сами клиенты используют этот gateway.

При `AUTH_REQUIRED` для stdio проверьте `agent-kit mcp creds status`, импортируйте отсутствующие значения и перезапустите клиент. Для remote MCP заново завершите OAuth в соответствующем клиенте и профиле. Ротация credentials выполняется повторным импортом и действует при следующем запуске MCP без `resync`. Изменение определения сервера или команды требует `resync`. `agent-kit mcp creds clear --yes` очищает только локальное хранилище credentials Kit, не OAuth-состояние клиента или Docker Desktop. После настройки выполните `agent-kit security scan`.

Ядро: Codebase Memory отвечает за граф кода и анализ влияния, Serena — за символы и рефакторинг, Context7 — за актуальную документацию, Sentry — за read-only исследование ошибок, issues, traces и release health. Эти инструменты не взаимозаменяемы. Условные GitHub, GitLab, SonarQube, Playwright и Atlassian активируются по признакам проекта; проект из нескольких репозиториев может одновременно включить несколько систем управления исходным кодом.

## Границы и маршрутизация

| MCP | Единственная основная роль | Когда не вызывать |
|---|---|---|
| Codebase Memory | граф архитектуры, вызывающие и вызываемые функции, влияние между репозиториями | для точечного чтения уже известного символа |
| Serena | поиск символов и ссылок, семантическое редактирование и рефакторинг | для общей карты зависимостей всего рабочего пространства |
| Context7 | актуальная внешняя документация библиотеки, фреймворка или API | для анализа локального исходного кода |
| Sentry | чтение ошибок, issues, traces, проектов и release health | для изменения issues или конфигурации Sentry: базовый профиль предоставляет только `inspect` |
| GitHub / GitLab | операции с репозиториями, задачами и PR конкретного провайдера | если провайдер не обнаружен в логическом проекте |
| SonarQube | существующие серверные замечания по качеству | вместо локальных тестов или проверки кода |
| Playwright | взаимодействие с браузером и проверка веб-интерфейса | для проекта без веб-интерфейса |
| Atlassian | контекст совместной работы в Jira и Confluence | без настроенного пространства или OAuth |

Сначала выбирается один MCP по требуемому виду подтверждений. CBM и Serena разрешено сочетать последовательно: граф определяет область влияния, затем Serena уточняет символы и ссылки. Параллельный широкий поиск обоими инструментами без конкретной причины считается избыточным. Каждый MCP хранит нативное состояние отдельно и регистрируется именем `agent-kit-<id>` в собственном пространстве имён, поэтому команды, базы данных и кэши не пересекаются.

CBM устанавливается закреплённым установщиком выпуска из точной ревизии источника, с явным URL выпуска и обязательной проверкой SHA-256; `curl | bash` не используется. Это соответствует версии 0.11, где `update` лишь направляет к локальному скрипту установки.

Sentry опционален, по умолчанию находится в локальном blocklist и запускается закреплённым пакетом `@sentry/mcp-server` через `npx` только после `agent-kit mcp enable sentry`. Перед синхронизацией и запуском AI-клиента передайте `SENTRY_ACCESS_TOKEN` через окружение. Для self-hosted инсталляции задайте `SENTRY_HOST` как hostname с необязательным портом, без `https://` и пути. Значения секретов не хранятся в YAML и не выводятся диагностикой.

## Docker MCP Toolkit

`docker-toolkit.yaml` задаёт переносимый контракт выделенного профиля `agent-engineering-kit`. Локальные файлы `overrides/global/docker-toolkit.yaml` и `overrides/projects/<project-id>/docker-toolkit.yaml` могут включить runtime и заменить mappings без изменения Git.

Подтверждённая таблица маршрутизации хранится в `<data>/state/docker-mcp-toolkit.json`. Пока `agent-kit mcp docker sync` не завершился успешно, регистрация клиентов не переключается. Для выбранных серверов Kit удаляет namespaced native registration и создаёт один gateway `agent-kit-docker`; остальные MCP продолжают работать нативно.
