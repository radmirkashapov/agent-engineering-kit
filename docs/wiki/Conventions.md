# Соглашения

## Язык

Пользовательские инструкции, сообщения проверок и Wiki пишутся естественным русским языком. Идентификаторы, команды, названия протоколов и API не переводятся. Переносимые значения `role` и `description` в каталогах `agents/`, `skills/`, `mcp/` и адаптерах клиентов по умолчанию остаются на английском. Если термин нужен читателю в исходном виде, оформляйте его как идентификатор.

## Состояние и секреты

- В Git хранятся переносимые и версионируемые определения.
- Не коммитьте учётные данные, локальные модели, личные переопределения, память, базы MCP, состояние клиента и созданные при запуске файлы.
- Используйте стабильный project.id; не переиспользуйте один ID для разных корней.
- Не копируйте Kit внутрь продуктового репозитория.
- Не выдавайте planned_capabilities за реально применённое разрешение.

## Git workflow

Создавайте ветку до изменений. Формат: <type>/dd-MM-yyyy-<description>, например docs/27-10-2026-github-wiki. Типы веток: feat, fix, refactor, docs, test, chore, ci, style и ai.

Сообщение коммита соответствует формату Conventional Commits:

```text
<type>(<scope>): <description>
```

Допустимые типы коммита: `feat`, `fix`, `test`, `refactor`, `style`, `ci`, `chore`, `docs`. Описание начинается со строчной буквы и формулируется в повелительном наклонении. Прямая отправка в `main` запрещена; изменения доставляются через PR и CI.

## Документация и проверки

Канонические знания хранятся в docs/ и индексируются через docs/INDEX.md. README объясняет эксплуатацию, ADR фиксируют решения, временные заметки не заменяют документацию. После контрактного изменения обновляйте затронутые страницы и проверяйте относительные ссылки.
