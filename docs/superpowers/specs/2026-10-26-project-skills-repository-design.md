# Репозиторий проектных skills

## Статус

Согласованный архитектурный дизайн. Реализация команд и форматов начнётся после отдельного просмотра этого документа.

## Задача

Несколько разработчиков и AI-агентов должны использовать общие skills одного logical project, даже если проект состоит из нескольких независимых Git-репозиториев. Skills должны проходить обычный командный процесс: ветка, commit, push, Pull Request или Merge Request, review и merge в `main`.

При этом Agent Engineering Kit не должен копировать skills в продуктовые репозитории, управлять их Git-историей или требовать специальный корневой checkout. Разработчик, у которого открыт только один репозиторий многорепозиторного проекта, должен получать тот же согласованный набор skills.

## Решение

Для каждого logical project используется отдельный обычный Git-репозиторий `project-skills`. Он является единственным источником проектных skills. По умолчанию Agent Engineering Kit читает состояние его ветки `main`, а для локальной проверки позволяет временно выбрать конкретную удалённую ветку.

Agent Engineering Kit отвечает только за получение, проверку, активацию и публикацию skills в поддерживаемые agent harness. Создание веток, commits, push, PR/MR и merge выполняются стандартными командами Git и средствами GitHub или GitLab.

## Привязка к logical project

Каждый продуктовый репозиторий logical project содержит собственный `.ai-team/project.yaml`. Связанные репозитории используют одинаковый `id`: этот идентификатор служит namespace проекта и ключом для локального состояния. Отдельный root-репозиторий не требуется.

Manifest объявляет источник skills:

```yaml
# Все репозитории с одинаковым id используют единое хранилище проектных skills.
version: 1
id: delivery-platform
name: Delivery Platform

skills:
  repository:
    # Поддерживаются обычные SSH- и HTTPS-адреса Git.
    url: git@gitlab.example.com:delivery/project-skills.git
    # После merge новые skills становятся доступны при следующем resync.
    default_branch: main
```

Одинаковый `id` без одинаковой ссылки на skills считается ошибкой конфигурации. Это предотвращает незаметное расхождение наборов skills в разных репозиториях одного logical project.

## Структура `project-skills`

Репозиторий остаётся обычным репозиторием skills без дополнительной системы scope:

```text
project-skills/
├── README.md
└── skills/
    ├── release-check/
    │   └── SKILL.md
    └── api-compatibility/
        ├── SKILL.md
        └── references/
```

Каждый корректный каталог в `skills/` доступен всему logical project. Если в будущем понадобится ограничивать skill по компонентам, это оформляется отдельным архитектурным решением, а не неявными соглашениями в именах каталогов.

## Локальный managed checkout

Agent Engineering Kit хранит технический checkout вне продуктовых репозиториев:

```text
<data-dir>/projects/<project-id>/skills-repository/
```

Этот checkout принадлежит Kit и не предназначен для ручной разработки. `resync` выполняет `fetch`, разрешает выбранную удалённую ветку в конкретный commit и активирует проверенную ревизию. Продуктовый working tree, его branch, index и незакоммиченные изменения не затрагиваются.

Git-аутентификация остаётся обязанностью стандартного окружения пользователя: SSH agent, credential helper или системное хранилище. Kit не копирует Git-токены в конфигурацию клиентов.

## Выбор ветки

По умолчанию используется `default_branch`, то есть `main`. Для проверки PR/MR разработчик может выбрать удалённую ветку для текущего project namespace:

```bash
agent-kit project skills use-branch feat/new-release-check
agent-kit project skills status
agent-kit resync
```

Возврат к согласованному состоянию:

```bash
agent-kit project skills use-main
agent-kit resync
```

Выбор ветки:

- хранится только на компьютере пользователя и не попадает в Git;
- применяется ко всем локальным репозиториям с тем же `project.id`;
- указывает на ветку удалённого `project-skills`, а не подключает произвольный локальный checkout;
- не изменяет `default_branch` в `.ai-team/project.yaml`;
- игнорируется режимом `validate --ci`.

Отдельных режимов для локального checkout, копирования skills или двусторонней синхронизации не вводится.

## Алгоритм `resync`

Для проектных skills `resync` выполняет следующие действия:

1. Определяет logical project по ближайшему `.ai-team/project.yaml`.
2. Берёт URL репозитория и ветку: локальный override либо `default_branch`.
3. Под project-level lock обновляет managed checkout и разрешает ветку в commit SHA.
4. Собирает candidate-набор skills из `skills/`.
5. Проверяет структуру и применяет существующий security pipeline для skills.
6. Атомарно переключает указатель активной ревизии только после успешной проверки.
7. Публикует effective skills через существующие thin adapters поддерживаемых клиентов.

`resync` не выполняет commit, push, merge или создание PR/MR.

## Отказоустойчивость и безопасность

Активная ревизия отделена от загруженной candidate-ревизии. Если ветка отсутствует, загрузка оборвалась или новый skill не прошёл проверку, Kit сохраняет последнюю успешно активированную ревизию и возвращает понятный статус `UPDATE_REJECTED`.

При отсутствии сети уже активированные skills продолжают работать. Статус сообщает, что источник устарел, и показывает SHA последней активной ревизии. Первая настройка без доступного репозитория завершается ошибкой, потому что безопасной предыдущей ревизии ещё нет.

Обновление сериализуется project-level lock. Поэтому одновременные `resync` из нескольких репозиториев одного namespace не повреждают checkout и не публикуют частично проверенный набор.

Перед активацией используются действующие проверки Agent Engineering Kit, включая проверку структуры skill, анализ инструкций и поиск секретов доступными средствами security pipeline. Конкретный набор инструментов определяется effective policy; отсутствие необязательного внешнего сканера отражается в отчёте, но не подменяется молчаливым успехом.

## Приоритет источников

Project skills образуют отдельный версионируемый слой. Итоговый порядок разрешения:

1. встроенные skills Agent Engineering Kit;
2. подключённые внешние catalog skills;
3. skills из `project-skills` текущего logical project;
4. явно разрешённые пользовательские local overrides.

Коллизия идентификаторов должна быть видна в `status` и provenance. Неявное объединение содержимого двух skills запрещено: выбирается один источник по установленному порядку.

## Наблюдаемость

`agent-kit project skills status` и отчёт `resync` показывают:

- `project.id` и URL источника;
- default branch и наличие local branch override;
- запрошенную ветку и разрешённый remote commit SHA;
- активный commit SHA и время последнего успешного обновления;
- состояние `ACTIVE`, `STALE`, `UPDATE_REJECTED` или `NOT_CONFIGURED`;
- причину отказа и сохранённую последнюю рабочую ревизию;
- provenance каждого активного project skill.

Секреты и credential URL в выводе маскируются.

## Работа команды

Типовой цикл выглядит так:

1. Разработчик клонирует `project-skills` как обычный репозиторий.
2. Создаёт ветку по командным Git-конвенциям и изменяет skill.
3. Делает commit, push и открывает PR/MR.
4. Для локальной проверки выбирает эту ветку командой `use-branch` и запускает `resync`.
5. После review изменения объединяются в `main`.
6. Остальные разработчики получают новую ревизию при следующем `resync`.
7. Автор возвращает локальное окружение на `main` командой `use-main`.

Для многорепозиторного проекта цикл не меняется: любой продуктовый репозиторий с тем же `project.id` использует один managed checkout и одну выбранную на компьютере ветку.

## CI

`agent-kit validate --ci` никогда не применяет machine-local branch override. CI проверяет объявленную default branch либо явно переданную immutable-ревизию, если такой параметр будет добавлен в реализацию. Результат должен содержать проверенный commit SHA, чтобы отчёт можно было воспроизвести.

## Изменения документации при реализации

Одновременно с командами необходимо обновить:

- главный `README.md`: назначение `project-skills`, быстрый старт и ежедневный workflow;
- справку `agent-kit help` и `--help` для `project skills`;
- шаблон `.ai-team/project.yaml` с русскими комментариями;
- руководство по multi-repo проектам и диагностике ошибок Git-доступа;
- `docs/INDEX.md` как карту канонической документации.

Документация не должна обещать команды до их появления в рабочей версии.

## Проверки реализации

Автоматические тесты должны покрыть:

- первое получение `main` и повторное обновление после нового commit;
- выбор ветки, возврат на `main` и общее состояние для двух репозиториев с одним `project.id`;
- независимость проектов с разными `project.id`;
- отсутствующую ветку и сохранение последней рабочей ревизии;
- невалидный или небезопасный skill без активации candidate;
- работу без сети при наличии активной ревизии;
- параллельные `resync` и атомарность активации;
- маскирование credentials в статусе;
- игнорирование local override в CI;
- публикацию project skills в поддерживаемые thin adapters.

## Вне области решения

В эту архитектуру намеренно не входят:

- управление Git-ветками, commits, push и PR/MR из Agent Engineering Kit;
- копирование общих skills в продуктовые репозитории;
- подключение произвольного локального checkout вместо managed checkout;
- автоматическое разрешение Git-конфликтов;
- отдельные skills для каждого product repository внутри одного namespace;
- синхронизация между несколькими репозиториями `project-skills`.

Такой минимальный контракт сохраняет привычный Git workflow и даёт всем репозиториям logical project единый, проверяемый и воспроизводимый набор skills.
