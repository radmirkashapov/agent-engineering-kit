# Основа harness control plane

Статус: согласовано к реализации 9 октября 2026 года.

## Цель

Закрепить `agent-engineering-kit` как управляющий слой для внешних agent harness. Набор определяет действующие роли, skills, MCP, правила, локальные переопределения и клиентские адаптеры, но не реализует собственный цикл модели, sandbox, approvals или жизненный цикл задач.

## Граница ответственности

Архитектура разделена на три уровня:

1. `agent-engineering-kit` — control plane и компилятор эффективной политики;
2. Codex, Claude Code, Claude Desktop, OpenCode и Cline — внешние execution harness;
3. будущий orchestrator — отдельный необязательный слой для очередей, worktree, повторных запусков и Pull Request.

Команда `resync` материализует первый уровень и описывает контракт со вторым. Она не запускает задачи и не принимает решения за runtime клиента.

## Контракт клиентского harness

Каждый клиент в `catalog/clients.yaml` получает:

- краткое английское описание;
- перечень возможностей, которыми управляет Kit;
- перечень возможностей, делегированных клиенту;
- явного владельца execution loop.

К управляемым возможностям относятся инструкции, skills и MCP. К делегированным — цикл агента, контекстное окно, sandbox, approvals, жизненный цикл задач и поток событий. Контракт описывает интеграцию Kit, а не обещает все функции конкретного продукта.

`agent-kit config explain` показывает выбранную границу ответственности. `resync` сохраняет тот же контракт и SHA-256 эффективной политики в `effective-environment.json`, чтобы состояние сеанса можно было воспроизвести.

## Роли агентов

Базовый набор содержит ровно пять обязательных ролей:

- `orchestrator` — принимает задачу, выбирает процесс и координирует передачу работы;
- `architect` — определяет границы, интерфейсы и последствия архитектурных решений;
- `developer` — реализует согласованное изменение с тестами;
- `reviewer` — независимо ищет дефекты, регрессии и пробелы в проверках;
- `qa-engineer` — воспроизводимо подтверждает критерии приёмки.

Каждая роль подробно описывает назначение, входы, обязанности, рабочий процесс, результат, ограничения, эскалацию и критерии передачи. Валидация завершается ошибкой, если роль отсутствует или появился неизвестный базовый идентификатор.

## Язык базовых определений

Английский является обязательным языком переносимых описаний по умолчанию:

- поле `role` и содержимое файлов `agents/*.md`;
- поле `description` first-party skills;
- поле `description` MCP-серверов;
- поле `description` клиентских harness.

Пользовательская документация, комментарии YAML, сообщения CLI и правила проекта остаются на русском. Это исключение фиксируется в `rules/documentation.md`, схемах, валидации и тестах репозитория.

## Локальная свобода пользователя

Пользователь может локально отключить, расширить или полностью заменить любой skill или MCP, включая элементы с признаками `required`, `locked` и `enforced`. Эти признаки описывают базовый профиль, но не блокируют владельца машины.

Свобода применяется только к данным вне Git. CI по-прежнему проверяет канонический репозиторий без локальных входов, а некорректная итоговая конфигурация не активируется.

## Манифест логического проекта

Новые проекты получают необязательный раздел `harness`:

```yaml
# Требования проекта к интеграции с внешним execution harness.
harness:
  preferred_client: auto
  required_capabilities:
    - instructions
    - skills
    - mcp
```

Значение `auto` сохраняет свободу выбора и выбирает первый совместимый адаптер. Явный client ID требует, чтобы его управляемые возможности покрывали требования проекта. Старые манифесты без раздела остаются валидными.

## Проверка

Приёмка включает:

- отрицательный тест для отсутствующих базовых ролей;
- проверку английского языка переносимых описаний;
- проверку схем MCP и клиентов;
- проверку capability contract и выбора `auto`;
- проверку полного локального `replace` для обязательного компонента;
- проверку вывода `config explain`;
- проверку manifest сеанса после `resync`;
- полный набор тестов и `agent-kit validate --ci`.

## Не входит в изменение

- собственный model loop;
- универсальный sandbox или approval broker;
- очередь задач и управление worktree;
- сбор телеметрии в отдельное хранилище;
- гарантии возможностей внешних продуктов за пределами интеграции Kit.
