# Дизайн автоматического workflow задач и контекста PR/MR

## Назначение

Agent Engineering Kit предоставляет два уровня управления:

- `agent` запускает типовой автоматический workflow разработчика;
- `agent-kit` предоставляет явные команды настройки, диагностики и восстановления.

Kit может создавать ветку и worktree, но не выполняет commit, push, создание или изменение PR/MR. Эти действия остаются обычными операциями Git и forge CLI.

## Инициализация проекта

`agent-kit project init` в интерактивном терминале предлагает шаблоны из `catalog/project-templates.yaml`. Каталог является версионируемой конфигурацией Kit: язык, стек, тип проекта, создаваемые файлы и рекомендуемый `.gitignore` не зашиты в CLI.

В неинтерактивном режиме те же значения передаются параметрами. Если Git-репозитория нет, команда выполняет `git init` с выбранной основной веткой. Существующие файлы не перезаписываются.

## Автоматическая задача

```text
agent task create <jira-url-or-task-id> [--type <type>]
```

Команда находит logical project по текущему каталогу, пытается прочитать Jira-задачу через разрешённый Atlassian MCP и создаёт task workspace, локальную бронь области изменений, ветку и worktree.

Если Jira недоступна или идентификатор не найден, идентификатор всё равно используется. Summary в таком имени ветки отсутствует. `--type` имеет приоритет над типом Jira-задачи и типом по умолчанию.

Форматы:

```text
<type>/dd-MM-yyyy-<task-id>-<summary>
<type>/dd-MM-yyyy-<task-id>
```

При конфликте имени добавляется `-copy-N`. Новая ветка создаётся от зафиксированного base commit, а не от существующей ветки задачи.

Локальная бронь, ранее называвшаяся lease, не синхронизируется между компьютерами. Она предотвращает только пересечение write set у параллельных задач на одной машине. Обычный сценарий управляет бронью автоматически.

При пересечении write set более поздняя задача получает состояние `WAITING`. Перед записью агент проверяет состояние через `task status`, а изменение write set требует повторной проверки. `task status` показывает блокирующую задачу и пересекающиеся пути. Локальная очередь не переносится между компьютерами: источником межмашинной синхронизации остаются Git remote, PR/MR, CI и серверная merge queue.

## Параллельные agent lanes

Внутри задачи агенты работают в отдельных lane-ветках и worktree, созданных от общего task base. Один branch нельзя одновременно использовать в нескольких worktree. Task-ветка является интеграционной, а lane-ветки получают префикс `agent/` и отдельный write set.

Непересекающиеся lane могут работать параллельно. Изменения общих файлов ставятся в локальную очередь и получают право записи последовательно. Kit не выполняет commit или merge: `lane integrate` проверяет локальный статус lane и выводит обычные Git-команды для разработчика или агента. После внешнего Git merge `lane complete` проверяет ancestry, освобождает общую область и активирует следующие lanes в порядке создания. Актуальность remote и обязательные проверки перед merge обеспечиваются обычным Git/forge workflow и CI.

Ручной fallback:

```text
agent-kit task create TASK-123 --type feat --summary orders --write 'services/orders/**'
agent-kit task status TASK-123
agent-kit task retry TASK-123
```

Проект определяется по текущему каталогу; `--project` нужен только при запуске снаружи.

## Контекст PR/MR

```text
agent-kit pr refresh [url-or-number]
```

Без аргумента команда определяет текущий Git-репозиторий и ветку, затем через официальный GitHub или GitLab MCP ищет открытые PR/MR. GitHub фильтрует по head branch на сервере; для GitLab Kit получает открытую страницу MR и точно фильтрует `source_branch` локально, потому что официальный tool не принимает такой фильтр. Один результат выбирается автоматически, несколько результатов предлагаются в интерактивном меню, а в non-interactive режиме требуют явного выбора.

URL имеет приоритет при выборе провайдера, затем используется remote текущего репозитория, затем GitLab как значение по умолчанию. В multi-repo проекте используется репозиторий текущего каталога; из общего корня требуется `--repository`.

Снимок хранится только в локальной памяти проекта. Данные PR/MR считаются недоверенными, ограничиваются по размеру и не интерпретируются как инструкции.

## Serena

Serena запускается с `--open-web-dashboard false`. Dashboard остаётся доступным вручную, но MCP-процесс не открывает вкладку при каждом старте.
