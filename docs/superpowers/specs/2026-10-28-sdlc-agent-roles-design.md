# Дизайн базовых SDLC-ролей агентов

## Контекст

Agent Engineering Kit уже поставляет роли `orchestrator`, `architect`, `developer`, `reviewer` и `qa-engineer`. Они покрывают реализацию и проверку, но не выделяют владельцев требований, безопасности, оценки поведения ИИ-агентов и выпуска. В результате эти обязанности приходится неявно распределять между существующими ролями.

Kit остаётся плоскостью управления: он описывает переносимые роли, требования к моделям и доступным инструментам, но не исполняет агентный цикл и не навязывает конкретный порядок запуска ролей. Выбор роли и передача работы выполняются поддерживаемым клиентом с учётом итоговой политики.

## Решение

Расширить обязательный базовый набор до девяти ролей:

1. `orchestrator` — координация полного жизненного цикла задачи;
2. `requirements-analyst` — формализация scope, acceptance criteria, assumptions и non-goals;
3. `architect` — системные границы, контракты, миграции и rollback;
4. `developer` — реализация согласованного изменения;
5. `reviewer` — независимая проверка корректности и сопровождаемости;
6. `security-engineer` — threat modeling и проверка рисков безопасности;
7. `qa-engineer` — продуктовая приёмка и регрессионная проверка;
8. `evaluation-engineer` — оценка поведения AI-агентов по traces, datasets и rubrics;
9. `release-engineer` — готовность выпуска, rollout, observability и rollback.

Новые роли не образуют обязательный линейный процесс. Orchestrator выбирает минимально достаточный набор для конкретной задачи. Например, небольшое исправление может пройти через developer, reviewer и qa-engineer, а изменение публичного протокола дополнительно потребует requirements-analyst, architect и security-engineer.

## Контракт роли

Каждый файл в `agents/` использует существующий frontmatter schema и подробное англоязычное описание. Роль обязана содержать:

- раздел о назначении и единственной зоне ответственности;
- наблюдаемые условия выбора роли;
- входные данные, без которых работа не начинается;
- обязанности и ожидаемые решения;
- порядок получения доказательств;
- проверяемые результаты;
- пределы полномочий и запрещённые подмены ответственности;
- условия остановки, эскалации и передачи работы;
- объективные условия завершения.

Поле `role` и весь текст роли остаются на английском. Русскоязычная пользовательская документация объясняет назначение набора, но не дублирует полные инструкции.

## Разделение ответственности

### Requirements Analyst и Architect

Requirements Analyst отвечает за проблему, границы, пользовательские результаты и проверяемые acceptance criteria. Architect принимает технические решения только после того, как продуктовая неопределённость устранена или явно эскалирована.

### Reviewer, Security Engineer и QA Engineer

Reviewer анализирует diff и его влияние на code health. Security Engineer рассматривает assets, trust boundaries, abuse cases, секреты, доступ и supply-chain risk. QA Engineer проверяет внешнее поведение и регрессии в целевом окружении. Ни одна из ролей не подменяет остальные одним общим verdict.

### QA Engineer и Evaluation Engineer

QA Engineer проверяет программный продукт по критериям приёмки. Evaluation Engineer проверяет вероятностное поведение ИИ-компонентов: выбор инструментов, передачу работы, соблюдение инструкций, устойчивость на представительном наборе данных и изменение метрик между ревизиями.

### Release Engineer

Release Engineer собирает доказательства готовности, проверяет совместимость, план развёртывания, наблюдаемость и откат. Роль не получает подразумеваемого разрешения на развёртывание, слияние, публикацию или изменение промышленной среды: такие действия выполняются только в пределах запроса пользователя и возможностей клиента.

## Модели и инструменты

Новые роли используют существующую политику моделей и только абстрактные идентификаторы инструментов, уже применяемые в Kit:

- `requirements-analyst`: reasoning, long context, code search и MCP;
- `security-engineer`: reasoning, coding, tool use, code search, diff и tests;
- `evaluation-engineer`: reasoning, coding, tool use, tests и MCP;
- `release-engineer`: reasoning, coding, tool use, tests, Git diff и MCP.

Роли не объявляют песочницу, подтверждения или внешние интеграции активными: это остаётся ответственностью контракта возможностей клиента и итоговой политики.

## Изменения в репозитории

Первый запрос на слияние содержит только роли и связанную документацию:

- четыре новых файла `agents/*.md`;
- обновление `DEFAULT_AGENT_IDS`;
- обновление теста полного обязательного набора;
- обновление README, Wiki и `docs/INDEX.md`;
- синхронное изменение версии пакета.

Skills и profiles не входят в этот Pull Request. Они будут спроектированы и реализованы отдельно после слияния ролей.

## Проверка

Проверки должны доказать:

- наличие ровно девяти обязательных default roles;
- соответствие каждого frontmatter схеме;
- англоязычность `role` и всего переносимого определения;
- достаточную подробность каждой роли;
- отсутствие неизвестных default roles;
- прохождение `agent-kit validate --ci` и полного набора тестов;
- согласованность версии и русскоязычной пользовательской документации.

## Источники решения

- Anthropic рекомендует начинать с простых, композиционных agent patterns и добавлять сложность только при измеримой необходимости: <https://www.anthropic.com/engineering/building-effective-agents>.
- OpenAI разделяет анализ отдельных traces и повторяемые evaluations на datasets: <https://developers.openai.com/api/docs/guides/agent-evals>.
- NIST SSDF рассматривает безопасность как набор outcomes на всём SDLC: <https://csrc.nist.gov/projects/ssdf>.
- Google Engineering Practices отделяет независимый code review от авторской реализации и проверяет design, functionality, complexity, tests и documentation: <https://google.github.io/eng-practices/review/>.

## Не входит в объём

- автоматический запуск ролей в фиксированной последовательности;
- новый движок процессов;
- новые skills или изменение profiles;
- автоматическое назначение моделей вне effective policy;
- разрешение развёртывания, слияния или внешних изменяющих действий;
- изменение логики `agent-kit project init`.
