# Управление MCP и skills через локальные overrides

Статус: согласовано к реализации 23 сентября 2026 года.

## Цель

Расширить Agent Engineering Kit так, чтобы пользователь мог без изменения базового репозитория:

- заменить реализацию любого skill;
- изменить конфигурацию любого MCP;
- разрешить или отключить любой MCP или skill, включая `required`, `locked` и `enforced` компоненты;
- выполнять те же операции командами CLI или ручным редактированием YAML;
- получить после установки готовые безопасные примеры конфигурации;
- понять структуру проекта и механизм переиспользования модулей по README.

YAML является единственным источником истины. CLI не ведёт отдельную базу настроек, а атомарно редактирует те же файлы, которые доступны пользователю вручную.

## Текущее состояние

Функция `apply_local_overrides` последовательно применяет глобальные и проектные файлы с режимами `extend`, `replace` и `disable`. Отдельные необязательные компоненты уже можно отключать, но:

- `required`, `locked` и `enforced` компоненты защищены от отключения;
- единого allowlist или blocklist нет;
- отключённые элементы исчезают из обычного списка и их трудно повторно включить;
- относительный путь к локальной реализации skill не имеет определённой базы разрешения;
- установщик создаёт каталоги overrides, но не наполняет их документацией и примерами;
- CLI не умеет создавать, включать, отключать и сбрасывать overrides.

## Принятые решения

### Полная свобода пользователя

Локальный пользователь может отключить любой MCP или skill. Признаки `required`, `locked` и `enforced` сохраняются в базовых определениях и отображаются как предупреждения, но больше не запрещают локальное отключение.

Корпоративные проверки исходного репозитория остаются обязательными. Свобода относится только к локальной итоговой конфигурации машины и не изменяет закоммиченный каталог.

### Два равноправных интерфейса

Поддерживаются одновременно:

1. ресурсные команды `agent-kit skills ...` и `agent-kit mcp ...`;
2. ручное редактирование файлов в `<data>/overrides/`.

Результат одинаков при любом способе. Каждая команда CLI сначала читает актуальный YAML, затем изменяет минимальную часть документа, валидирует результат и записывает его атомарно.

## Структура локальных данных

После `agent-kit install` или первого `resync` существует следующая структура:

```text
<data>/overrides/
├── README.md
├── global/
│   ├── access.yaml
│   ├── mcp/
│   │   └── github.yaml.example
│   ├── skills/
│   │   └── greeting.yaml.example
│   └── sources/
├── projects/
│   └── README.md
├── examples/
│   ├── access.yaml
│   ├── mcp/
│   └── greeting/
│       ├── SKILL.md
│       └── scripts/
│           └── greet.py
└── backups/
```

Установщик создаёт только отсутствующие файлы и никогда не перезаписывает пользовательские данные. Файлы `.yaml.example` не участвуют в разрешении конфигурации.

При первом изменении уровня проекта создаются:

```text
<data>/overrides/projects/<project-id>/
├── access.yaml
├── mcp/
├── skills/
└── sources/
```

## Формат управления доступом

Новый файл `access.yaml` проверяется отдельной JSON Schema:

```yaml
# Управляет доступностью MCP и skills на этом уровне.
version: 1

mcp:
  # Пустой allow не ограничивает базовый каталог.
  allow: []
  # Block применяется после allow и полностью отключает компонент.
  block: []

skills:
  allow: []
  block: []
```

Для каждого вида компонентов действуют правила:

- отсутствующий или пустой `allow` означает полный исходный набор;
- непустой `allow` оставляет только перечисленные ID;
- `block` всегда применяется после `allow`;
- один ID в `allow` и `block` одного документа является ошибкой;
- неизвестный ID является ошибкой;
- повторяющиеся ID являются ошибкой схемы;
- любой известный ID разрешено заблокировать.

Глобальный и проектный уровни объединяются монотонно:

```text
effective = catalog
          ∩ global allow, если он непуст
          ∩ project allow, если он непуст
          − global block
          − project block
```

Проект не может повторно разрешить глобально заблокированный компонент. Пользователь сохраняет полную свободу: глобальный запрет снимается изменением глобального файла или командой с `--scope global`.

## Порядок разрешения конфигурации

Для MCP и skills используется единый порядок:

1. загрузить базовый каталог и lock-файлы;
2. загрузить глобальные и проектные определения overrides;
3. проверить ссылки, схемы и относительные пути;
4. применить `extend` и `replace` к определениям;
5. вычислить решение доступа из `access.yaml` и `disable`-overrides;
6. сохранить причины решения для `available`, `status` и `explain`;
7. устанавливать, публиковать и регистрировать только включённые компоненты.

Режим `disable` сохраняется для обратной совместимости и трактуется как локальная блокировка целевого ID. Новый CLI записывает доступ через `access.yaml`, а существующие `disable`-файлы продолжают работать.

## Команды CLI

Существующие пространства команд расширяются симметрично:

```text
agent-kit skills available
agent-kit skills enable <id> --scope global|project [--resync]
agent-kit skills disable <id> --scope global|project [--resync]
agent-kit skills override <id> --from <directory> --scope global|project [--resync]
agent-kit skills reset <id> --scope global|project [--resync]
agent-kit skills explain <id>

agent-kit mcp available
agent-kit mcp enable <id> --scope global|project [--resync]
agent-kit mcp disable <id> --scope global|project [--resync]
agent-kit mcp override <id> --from <yaml> --scope global|project [--resync]
agent-kit mcp reset <id> --scope global|project [--resync]
agent-kit mcp explain <id>
```

Изменяющие команды требуют явный `--scope`. Для `project` должен быть найден `.ai-team/project.yaml`; иначе команда завершается ошибкой без изменения файлов.

`available` читает полный каталог до фильтрации и показывает:

- ID и источник;
- базовую обязательность;
- решение доступа на каждом уровне;
- итоговое состояние `enabled`, `disabled` или `inactive`;
- причину решения.

`inactive` означает, что MCP разрешён, но не активирован признаками проекта. `disabled` означает явный запрет пользователя.

### Изменение доступа

`enable` удаляет ID из `block` выбранного уровня и добавляет его в непустой `allow`. `disable` удаляет ID из `allow` и добавляет его в `block`. Команда сообщает, если более высокий уровень продолжает блокировать компонент.

Отключение обязательного компонента разрешено, но сопровождается предупреждением о потерянной возможности.

### Переопределение skill

`skills override --from <directory>` требует каталог с валидным `SKILL.md`. Каталог копируется в `<scope>/sources/skills/<id>/`, затем создаётся override с режимом `replace` и относительным путём к копии. Относительный `value.path` всегда разрешается относительно YAML-файла override, поэтому конфигурация переносима.

### Переопределение MCP

`mcp override --from <yaml>` принимает документ с полями `mode` и `value`. CLI добавляет проверенный `target`, запрещает буквальные секреты и сохраняет итоговый документ как `<scope>/mcp/<id>.yaml`.

### Сброс

`reset` удаляет ID из `allow` и `block`, а активный файл определения и локальный source переносит в `<data>/overrides/backups/<utc-timestamp>/`. Безвозвратного удаления нет.

## Демонстрационный skill `greeting`

Базовый first-party skill `greeting` отвечает простым приветствием:

```text
Привет!
```

Установочный пример содержит альтернативный `SKILL.md` и переносимый Python-скрипт на основе `getpass.getuser()`. После команды:

```bash
agent-kit skills override greeting \
  --from <data>/overrides/examples/greeting \
  --scope global \
  --resync
```

skill возвращает:

```text
Привет, <имя пользователя>!
```

Удаление override возвращает базовое поведение. Пример не хранит имя, не читает секреты и работает в macOS, Linux и Windows.

## Архитектура реализации

Новый модуль управления доступом отвечает только за:

- загрузку и проверку `access.yaml`;
- объединение global/project policy;
- вычисление решения и причины для каждого ID;
- атомарное изменение allow/block.

Модуль overrides продолжает отвечать за `extend`, `replace`, `disable` и разрешение локальных источников. MCP manager, external skills manager и client sync используют общий результат resolver, чтобы списки, установка и регистрация не расходились.

CLI вызывает сервис управления overrides, а не редактирует YAML напрямую. Это позволяет тестировать операции без запуска subprocess.

## Ошибки и восстановление

- неизвестный ID, конфликт allow/block, неправильная схема или путь завершают операцию до записи;
- запись выполняется через временный файл и атомарную замену;
- `--resync` запускается только после успешной записи;
- ошибка `resync` не откатывает явно выбранную политику, но выводит путь к ней и команду возврата;
- `reset` создаёт резервную копию до изменения;
- `doctor` различает пользовательское отключение, отсутствие установки, отсутствие авторизации и ошибку конфигурации;
- literal-секреты запрещены, разрешены только ссылки `env:VARIABLE`.

## Локализация и YAML

Все пользовательские сообщения, комментарии, docstrings и документация пишутся профессиональным русским языком. Названия API, команд, продуктов и машинные идентификаторы не переводятся.

Каждый tracked YAML получает комментарии:

- о назначении файла;
- перед основными секциями;
- у параметров с неочевидными значениями или ограничениями;
- перед первым элементом повторяющейся структуры.

Сгенерированные YAML и примеры следуют тем же правилам.

## README и карта репозитория

README получает карту всех верхнеуровневых директорий. Для каждой директории указываются ответственность, связи с другими частями и способ переиспользования. Отдельные сценарии описывают:

- ручное управление YAML;
- команды `available`, `enable`, `disable`, `override`, `reset`, `explain`;
- базовый и переопределённый `greeting`;
- приоритет global/project;
- восстановление из backup;
- полное отключение обязательного компонента и последствия.

## Проверки

Разработка выполняется через TDD. Нужны тесты:

- схемы `access.yaml`;
- пустого и непустого allowlist;
- приоритета blocklist;
- глобального и проектного пересечения;
- отключения `required`, `locked` и `enforced` компонентов;
- обратной совместимости с `mode: disable`;
- относительных путей skill overrides;
- всех новых CLI-команд и обязательного `--scope`;
- идемпотентного создания примеров без перезаписи;
- резервного копирования при `reset`;
- отсутствия literal-секретов;
- одинакового результата CLI и ручного YAML;
- полного набора repository validation и клиентской синхронизации.

## Версия и совместимость

Изменение повышает minor-версию до `0.3.0`. Старые per-target overrides продолжают работать. Защитный запрет на локальное отключение обязательных компонентов снимается намеренно и документируется как несовместимое изменение политики, но не формата существующих файлов.
