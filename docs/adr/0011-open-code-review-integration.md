# ADR 0011: возможная интеграция OpenCodeReview

Статус: предложено для ограниченного пилота.

## Контекст

[Alibaba OpenCodeReview](https://github.com/alibaba/open-code-review) предоставляет CLI для проверки изменений и полных файлов. Он сочетает детерминированный выбор файлов и правил с LLM-агентом, умеет выдавать замечания с привязкой к строкам и предоставляет интеграции для Codex, Claude Code, OpenCode и CI.

На момент оценки основной README описывает `ocr` прежде всего как CLI и отдельно документирует подключение внешних MCP к агенту проверки. Одновременно [дорожная карта](https://github.com/alibaba/open-code-review/blob/main/ROADMAP.md) перечисляет MCP-сервер среди текущих возможностей. До закрепления и проверки конкретной ревизии нельзя считать MCP-контракт стабильным или определять по нему способ интеграции.

В наборе уже есть собственный skill `code-review`, роли `reviewer` и `auditor`, а также проверки Semgrep и SonarQube. Поэтому безусловное добавление OpenCodeReview создаст дублирование и ещё один контур конфигурации моделей, секретов и правил.

## Решение

Не включать OpenCodeReview в обязательные MCP или skills из коробки. Рассматривать его как необязательный внешний инструмент проверки кода. Форму подключения — CLI-адаптер, skill или MCP — выбрать только после проверки закреплённой ревизии в пилоте.

Для пилота:

1. закрепить точную версию пакета и контрольную сумму в отдельной записи каталога и lock-файла;
2. установить инструмент во внешнее локальное хранилище, не добавляя его исходный код в этот репозиторий;
3. прогнать Gitleaks, Semgrep и действующие проверки цепочки поставки до активации;
4. начать с режима делегирования, в котором текущий AI-клиент выполняет анализ без отдельного ключа модели для `ocr`;
5. предоставить один тонкий skill-адаптер, который запускает `ocr review --format json --output <path>` и передаёт результат штатному рецензенту;
6. не запускать одновременно полный `code-review` и полный обзор OpenCodeReview: один инструмент должен быть основным, второй — независимой проверкой только для рискованных изменений;
7. хранить сеансы, конфигурацию провайдера и отчёты вне Git.

## Критерии включения

Пилот можно перевести в поддерживаемую условную интеграцию, если зафиксированы лицензия и источник установки, установка воспроизводима на поддерживаемых платформах, секреты не попадают в Git и журналы, замечания не дублируют штатную проверку в неприемлемом объёме, а время и стоимость запуска оправданы найденными дефектами.

## Последствия

Текущий набор остаётся компактным и не получает второй обязательный механизм проверки. При этом путь интеграции документирован и совместим с существующей моделью желаемого состояния, безопасной активацией и локальным хранением данных.
