# 0014. Локальная политика, проектные skills и обновление индексов

Статус: proposed; реализация проверяется в отдельной ветке.

## Контекст

Корпоративные определения переносимы, но пользователь должен выбирать runtime-модель и локальный набор компонентов. Общий каталог публикации project-skills смешивал проекты. Одних инструкций об актуализации памяти недостаточно для Git-команд вне harness.

## Решение

Локальный model enforcement отделён от каталога providers и CI baseline. При отключении снимается структурированная model-привязка из сгенерированных копий skills и effective agents/rules. Исходники остаются источником истины; произвольная проза не переписывается.

Conventions включены в существующий overlay resolver, выбор allow/block доступен для всех видов компонентов. Каталоги проверяются отдельно от локальных результатов. Технический запрет секретов в Git сохраняется.

Проектные навыки публикуются в installations/clients/projects/<id>. Нативные project-каталоги содержат только небольшие namespaced загрузчики. Команда skills read проверяет ближайший logical project перед выдачей тела. Это предотвращает ошибочную загрузку root-навыка из nested проекта; доступ пользователя к локальным файлам не ограничивается.

Git post-commit/post-checkout/post-merge запускают фоновое обновление. Существующие hooks не переписываются. Resync повторно отмечает изменившийся проект, обеспечивая резервный путь. Очередь объединяет события под блокировкой; ошибки сохраняются отдельно от успешности Git-команды. Индекс связанного worktree получает отдельное имя.

Коллизии сохраняют обратную совместимость приоритета источников, но доступны provenance и явный skills prefer. Семантические противоречия skills с разными именами автоматически не разрешаются.

## Альтернативы

1. Переписывать корпоративные исходники локально: проще публикация, но появляются Git-конфликты и теряется baseline.
2. Публиковать все project-skills глобально: прежняя реализация, несовместима с независимыми проектами.
3. Полностью отдельный процесс клиента на каждый проект: сильнее изоляция, требует владения запуском harness и меняет пользовательский workflow.

Выбран локальный resolver и проверяемая загрузка. Цена — дополнительный CLI-вызов для тела project-skill и необходимость перезапуска существующей клиентской сессии после изменения discovery.

## Миграция и восстановление

Resync перестаёт помещать project-skills в global discovery и создаёт отдельные project exposures. Сгенерированные файлы не следует коммитить. Для возврата к модели baseline: models enforcement on и resync. Для восстановления выбора источника удаляется соответствующий локальный skill-sources/<id>.yaml. Откат версии требует повторного resync; локальные исходники overrides и корпоративный Git при этом сохраняются.

## Приёмка

Проверить исходники до/после model projection, CI без локальных входов, два project-ID одновременно, отказ skills read при nested mismatch, сохранение пользовательских hooks, повторную обработку событий, provenance всех совпадающих skill-ID и явный выбор источника. Проверки Windows-native и фактического поведения клиентского discovery должны подтверждаться отдельно от unit-тестов путей.
